## Change Logs & Versioning

The **Nigeria Core Implementation Guide Change Log** captures updates, enhancements, clarifications, and corrections across versions of the Nigeria Core FHIR Implementation Guide.

It will reflect stakeholder feedback, programme alignment, sandbox and Connectathon testing, terminology harmonisation, implementation experience, and alignment with national digital health governance and standards processes.

### How to Review Updates Between Versions

1. **Identify Your Starting Point:**Determine the Nigeria Core version. Review any intermediate ballot, draft, sandbox, or trial-use updates.
1. **Review Version Summaries:**Start with the version summary to identify major changes, new profiles, new guidance pages, terminology updates, and conformance changes.
1. **Examine Detailed Changes:**Review the changes table for affected pages, profiles, examples, terminology, CapabilityStatements, and operations.
1. **Compare Across Versions:**Use the [Changes Between Versions] section for detailed artefact comparisons where available.
1. **Check Programme Dependencies:**If implementing a derived programme IG, review both the Nigeria Core Change Log and the programme-specific Change Log.
1. **Validate Before Production:**Validate resources against the relevant Nigeria Core package and sandbox test scripts before production exchange.

### Versions [DRAFT]

The entries below list published, draft, ballot, trial-use, and patch versions of Nigeria Core. Implementers should review all versions between their current implementation and their intended target version before upgrading.

### Versioning of Nigeria Core [DRAFT]

Nigeria Core is expected to undergo periodic updates as national priorities, programme requirements, standards adoption, implementation feedback, and conformance testing mature.

The [Directory of Published Versions] lists the publication history with links to each released version of Nigeria Core. The [Change Log] documents changes across versions.

When a change significantly affects conformance testing, procurement, sandbox behaviour, or production implementation, it may be identified as a **patch candidate**. Patch candidates may be released between major versions where they are needed to correct errors, clarify requirements, or address urgent implementation issues.

Nigeria Core currently in draft releases may include:

* Draft releases for authoring and internal review.
* Ballot or stakeholder review releases.
* Trial-use releases for implementation and sandbox testing.
* Patch releases for corrections and clarifications.
* Stable releases aligned with national standards endorsement and production use.

### Nigeria Core Maturity Levels

Nigeria Core artefacts may be assigned maturity levels to help implementers understand their stability, expected reuse, and suitability for production implementation.

#### Profiles, Extensions, and Operations

* **Nigeria Core Maturity Level 5:** Stable artefacts widely implemented in production, tested through multiple implementation cycles, and aligned with national standards or formal policy requirements. Forward compatibility is expected.
* **Nigeria Core Maturity Level 4:** Stable artefacts that have completed substantial review and testing but may not yet be widely implemented across all settings. Forward compatibility is expected where feasible.
* **Nigeria Core Maturity Level 3:** Trial-use artefacts reviewed by stakeholders and suitable for sandbox, Connectathon, and pilot implementation. Forward compatibility is not guaranteed.
* **Nigeria Core Maturity Level 2:** Draft artefacts under active development, not yet widely implemented, and likely to change based on testing and stakeholder feedback.
* **Nigeria Core Maturity Level 1:** Early exploratory artefacts, examples, or candidate content used to gather feedback.

#### SearchParameters

Nigeria Core SearchParameters may be assigned maturity levels based on implementation experience. SearchParameters required for core patient, facility, provider, registry, Shared Health Record, and programme workflows should be treated as higher priority for stability and conformance testing. SearchParameters will prioritize EMR/EHR vendor suggested hospital uses.

#### ValueSets, CodeSystems, ConceptMaps, CapabilityStatements, and Requirements

Nigeria Core terminology and CapabilityStatement artefacts are expected to evolve as programme requirements, registry mappings, international terminology mappings, and implementation experience mature. Forward compatibility is not guaranteed unless explicitly stated.

### Endpoint Discoverability

A Nigeria Core Server may support multiple FHIR endpoints, versions, implementation modes, or programme-specific APIs. For example, an implementation may expose separate endpoints for production, sandbox, state-level exchange, programme-specific exchange, or Shared Health Record access.

The best practice is to inspect the FHIR endpoint metadata to discover the Server’s capabilities, including the FHIR version, supported Nigeria Core version, supported profiles, interactions, search parameters, operations, security model, and programme-specific capabilities.

`GET [base]/metadata{?mode=[mode]} {&_format=[mime-type]}`

Servers **SHOULD** declare supported Nigeria Core profiles in `CapabilityStatement.rest.resource.supportedProfile` and applicable Nigeria Core CapabilityStatements in `CapabilityStatement.instantiates`.

### No Guarantee that Resource IDs are Preserved

Servers **SHOULD** maintain stable identifiers for resources across versions. However, FHIR logical ids may change when data are migrated, transformed, synchronised, de-duplicated, or moved between systems.

When FHIR resource ids are not preserved, Clients **SHALL** use appropriate business identifiers, registry identifiers, patient identifiers, facility identifiers, provider identifiers, or other matching methods to avoid duplication.

Implementers **SHOULD** preserve identifiers such as:

* Patient identifiers.
* Facility registry identifiers.
* Health workforce identifiers.
* Professional regulator identifiers.
* Programme identifiers.
* Local EMR or facility identifiers.
* Shared Health Record identifiers.

### Version = 0.0.0 (Initial Nigeria Core / Stakeholder Review Release)

* Based on FHIR version: 4.0.1
* Package id: `ng.fhir.core`
* Publication status: Draft for presentation
* Intended maturity: Draft
* Realm: Nigeria

This initial release establishes the national baseline for FHIR-based interoperability across Nigeria’s health sector and supports stakeholder review, sandbox testing, Connectathon-style validation, vendor onboarding, and progressive standards endorsement.

#### What’s New

This release introduces:

* Nigeria Core Home page and overall IG structure.
* General conformance, Must Support, Security, and Programme Guidance pages.
* Guidance for clinical notes, medication management, basic Provenance, registries, shared services, and NHMIS/DHIS2 relationship.
* Relationship guidance for IPS, WHO SMART Guidelines/DAKs, Registries data, and programme IGs.
* NG Patient Summary guidance aligned with IPS and NIS ISO 27269 principles.
* Download page structure for packages, examples, LLM-ready files, CSV/Excel exports, terminology artefacts, and sandbox artefacts.
